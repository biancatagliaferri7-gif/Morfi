# Validación de salida a piloto

La versión integrada recupera `feature/bianca` en `22d1208fba73433a6e83035eeafee99db59af627`. El código de pedidos, la confirmación `/auth/callback`, el mapa y las reseñas son los de esa rama. No publicar nuevamente el código anterior de `main` ni inicializar de nuevo la base existente.

1. En el Supabase existente, ejecutar primero las consultas de lectura de `MORFI_CHECKOUT_VERIFICACION.sql`. Identificar qué migraciones de Bianca ya están instaladas. No ejecutar todas las variantes SQL del repositorio: `MORFI_CHECKOUT_LISTO.sql` y los tres archivos numerados son alternativas, no pasos acumulativos. Si faltan prerrequisitos, resolverlos antes de desplegar.
2. Para el proyecto MORFI `upsmoqivykcgvhhopckf`, el 9 de noviembre se aplicaron, en este orden, `MORFI_CHECKOUT_LISTO.sql`, `morfi_auth_business_registration_incremental.sql` y `morfi_reconciliation_migration.sql`. La base real usa `morfi_businesses.payment_methods text[]`; el nombre singular `payment_method` es un alias de salida de las RPC. No volver a ejecutar migraciones por suponer que el nombre singular es una columna. Antes de cualquier nueva ejecución, revisar el esquema y el historial del SQL Editor. La verificación posterior encontró `morfi_create_order_v2`, cotización de envío, trigger de alta de vendedor y RPC de configuración privada. Se restauró además el permiso de lectura de las columnas públicas del catálogo sin habilitar la lectura directa de datos bancarios. No había pedidos al momento de migrar.
   El 10 de noviembre se aplicó `morfi_order_history_incremental.sql` porque faltaba `morfi_order_status_history` y la pantalla «Mis pedidos» fallaba al consultar esa tabla. La migración registra el estado actual de los pedidos existentes, crea el historial para los nuevos cambios y permite leerlo solo a sus participantes. Verificar el pedido #2 en la cuenta compradora y en el panel del comercio después de recargar.
3. En Vercel, `VITE_SUPABASE_URL` y `VITE_SUPABASE_PUBLISHABLE_KEY` ya estaban configuradas para producción. El 9 de noviembre se agregó `VITE_MORFI_ORDER_CHECKOUT_V2=true` para producción; el despliegue `2b6c5fb` quedó Ready y asignado a `morfi-ten.vercel.app`. Vite fija esa variable al compilar. Comprobar en la URL pública que desapareció el mensaje de instalación de V2 antes de hacer pruebas de compra.
   Mientras V2 esté desactivado, el comprador puede registrar pedidos básicos con retiro o envío de tarifa definida; el checkout guarda su teléfono en `morfi_profiles` antes de llamar a la RPC anterior. Observaciones, referencias y envíos pendientes de cotización requieren V2. El bloqueo visible en el checkout no se elimina activando solo la variable: la migración debe estar instalada y verificada primero.
4. En Authentication → URL Configuration, usar `https://morfi-ten.vercel.app` como Site URL y permitir `/auth/callback`, `/login` y `/login?recovery=1` en ese dominio. Conservar `/auth/callback` para los enlaces de correo que puedan usarse más adelante. El 9 de noviembre se desactivó Authentication → Sign In / Providers → Confirm email para el piloto; el ajuste persistió después de recargar. Los registros nuevos pueden iniciar sesión sin esperar un mensaje de confirmación, pero la propiedad del correo no queda verificada. Volver a evaluar esta decisión antes de abrir el servicio al público general.
   En Authentication → Providers → Email, revisar la política real de contraseñas (longitud, tipos de caracteres y protección de claves filtradas). El formulario explica los motivos que devuelve Supabase; usar una contraseña nueva con mayúsculas, minúsculas, números y un símbolo. Una contraseña hecha solo con el DNI no es apropiada.
   El registro nuevo ya no depende del SMTP de confirmación. La recuperación de contraseña, el cambio de correo y cualquier enlace de verificación por correo sí dependen de un servicio de envío funcional. [Supabase indica](https://supabase.com/docs/guides/auth/testing-auth-flows) que su servicio integrado de prueba solo envía a direcciones de integrantes del equipo; para destinatarios externos se necesita SMTP propio o un Send Email hook. No presentar «Reenviar correo de verificación» como solución para las cuentas nuevas de este piloto. Si una cuenta creada antes de desactivar la confirmación sigue sin poder ingresar, revisar Authentication → Users y Logs; cambiar el ajuste no demuestra que esa cuenta anterior haya quedado confirmada.
5. Crear dos cuentas nuevas de prueba: comprador y vendedor. Probar tanto el registro rápido de vendedor como el completo con mapa y banco. Un DNI ya asociado a una cuenta impide crear otro emprendedor con ese mismo DNI; recuperar o usar la cuenta existente antes de volver a intentar el alta. El vendedor configura “Cómo vendés hoy”, publica un producto y una foto. Verificar que la foto se guarda como URL en Storage. El stock es opcional y no impide vender.
6. Desde el comprador, confirmar y reintentar el mismo pedido. Debe existir una sola orden; la venta no descuenta inventario. Probar retiro, envío gratis, tarifa fija y cotización pendiente. En esta última opción, no se puede despachar ni transferir antes de confirmar el costo.
7. Desde el vendedor, aceptar, preparar, marcar listo y entregar; revisar transferencia y rechazo/cancelación. Recargar ambos navegadores y comprobar Realtime o la actualización de respaldo cada 30 segundos con pestaña visible. Un pedido nuevo sin descuento de inventario no debe generar stock al cancelarse.
8. Desde una tercera cuenta, intentar leer `morfi_managed_business_settings` con un comercio ajeno y modificar su stock: debe rechazarse. Verificar que los datos bancarios y teléfonos privados no se consulten directamente con anon. Probar producto retirado, comercio cerrado y pago no habilitado.
9. Instalar la PWA y probar red lenta, navegación directa a `/business`, texto ampliado y recuperación de sesión. Sin red se conserva el shell e imágenes públicas visitadas; pedidos y sesión requieren red. Confirmar reseñas después de una entrega.
10. Ejecutar `npm test` y `npm run build` sobre el commit que se despliega. Las pruebas locales de PostgreSQL usan un esquema mínimo, no sustituyen la validación autenticada de Supabase/Storage. Registrar las pruebas de uso con cinco personas antes de difundir la aplicación.
11. Opiniones: el catálogo tolera temporalmente una base sin las tablas de opiniones y muestra un aviso comprensible. Para habilitar las calificaciones y sus resúmenes, aplicar el bloque de reviews de `morfi_repair_existing_schema_incremental.sql` sobre la base existente; verificar luego `morfi_business_reviews`, `morfi_product_reviews`, `morfi_business_review_summary` y `morfi_product_review_summary` desde el Data API.
